# Работа команды

Общий репозиторий: [Final-Project-CGF](https://github.com/F1j1tun1/Final-Project-CGF). Рабочая база — C++17, OpenGL 3.3 Core и CMake; сцена и шейдеры реализованы в проекте. Правила внесения изменений и команды сборки находятся в [CONTRIBUTING.md](../CONTRIBUTING.md).

## Доступ и распределение задач

Владелец репозитория добавляет участников по их GitHub-логинам через настройки доступа. Этот документ не подтверждает, что доступ уже выдан; настройки репозитория им не меняются.

Для команды из трёх человек удобно такое распределение; при двух участниках объедините UI с графикой или правилами:

| Направление | Основные файлы | Результат |
| --- | --- | --- |
| Правила и баланс | `src/game/`, `tests/` | Состояния, улучшения, тесты, статистика по seed |
| 3D-графика | `src/graphics/`, `assets/shaders/` | Геометрия, камера, свет, текстуры и визуальные эффекты |
| UI и материалы сдачи | `src/main.cpp`, `docs/` | Экран игры, магазин, проверка сценариев, отчёт и демо |

Назначьте конкретных людей сами; роли не означают запрет другим участникам помогать. В issue или обсуждении задачи запишите ответственного, ожидаемое поведение и критерий готовности.

## Ежедневный цикл

1. Выберите небольшую задачу и согласуйте затрагиваемые файлы.
2. Сохраните текущую работу в своей ветке. Обновите локальный `main` через `git pull --ff-only origin main`, находясь на `main`, и создайте отдельную ветку.
3. Реализуйте изменение, запустите соответствующие проверки и просмотрите diff.
4. Отправьте ветку и откройте PR в `main` с результатами проверки.
5. Другой участник читает diff и при необходимости запускает игру. После замечаний автор обновляет ту же ветку.
6. После слияния остальные обновляют `main` перед следующей задачей.

Рекомендуем хранить `main` в собираемом состоянии и принимать будущие изменения через PR. Защита ветки и права доступа настраиваются владельцем отдельно. Не используйте force push для `main` и общих веток; не удаляйте работу коллег для устранения конфликта.

Если ваша рабочая ветка отстала, сначала сохраните собственные изменения. Объединение актуального `main` в свою ветку не переписывает её историю:

```powershell
git fetch origin
git merge origin/main
```

При конфликте согласуйте смысл обеих версий с автором, исправьте файлы и проверьте сборку. Если не уверены в результате, `git merge --abort` отменяет незавершённое слияние; не применяйте команды очистки к чужим несохранённым файлам.

## Общий `main.cpp`

Пока окно, UI и построение сцены находятся в одном файле. Перед параллельными изменениями укажите, кто его редактирует. Сначала сливайте один небольшой PR, затем обновляйте вторую ветку. При росте файла можно отдельной задачей вынести UI или анимации в модуль представления; не совмещайте это с изменением правил.

Анимации хранят время, позиции и повороты вне `Game`. Рендерер получает данные сцены; победитель, колода и награды остаются в игровом модуле. Это помогает участникам работать независимо и сохраняет воспроизводимость.

## Готовность задачи

Правила: тест изменённого поведения и успешный `core-only`. Графика/UI: сборка `desktop`, тесты, smoke-прогон при рабочем контексте и визуальная проверка изменённого сценария. Лог CI подтверждает только выполненные в нём проверки; успешный тест правил не подтверждает отображение света или карт.

В PR укажите ОС, команды и результат. Если GPU или другая платформа недоступны, запишите ограничение и договоритесь, кто проверит графику. Для ошибки используйте версию коммита, seed и действия, а для графики — также GPU и драйвер. Подробный формат issue — в CONTRIBUTING.

При обновлении сторонних библиотек сохраняйте лицензии и обновляйте сведения о версии, источнике и SHA-256. Для собственных ресурсов команды также фиксируйте происхождение и разрешение на использование.

## Следующие небольшие задачи

Это план дальнейшей работы, а не список уже реализованных возможностей:

1. Анимация раздачи и переворота карт: стабильные идентификаторы, сброс при restart, одинаковый исход с анимацией и без неё.
2. Звуки раздачи и эффектов: разрешённые ресурсы, регулировка громкости, отсутствие зависимости правил от звука.
3. Баланс: статистика по seed и стратегиям, обоснованные изменения целей, наград и улучшений.
4. Проверка чистой сборки на второй машине и машине преподавателя; фиксирование фактических результатов.
5. Демо на 3–6 минут, отчёт по шаблону курса и презентация с вкладом участников.
