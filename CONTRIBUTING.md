# Как участвовать в проекте

Jester Jack — учебная игра на **C++17 + OpenGL 3.3 Core**: шутовская 3D-сцена, 2D-интерфейс, бесконечные раунды по пять раздач на цель и магазин улучшений. Проигрыш отдельной руки не завершает забег; исчерпание раздач без цели завершает. Требование курса — собственный шейдерный конвейер. Сохраняем этот стек и небольшие проверяемые изменения. Имя CMake target и executable `blackjack_forge` оставлено для совместимости.

Перед первой задачей прочитайте [README](README.md), [AGENTS.md](AGENTS.md), [архитектуру](docs/ARCHITECTURE.md) и [порядок работы команды](docs/TEAM_WORKFLOW.md). Настройка компилятора и CMake описана в README.

## Получение проекта

```powershell
git clone https://github.com/F1j1tun1/Final-Project-CGF.git
cd Final-Project-CGF
```

Откройте эту папку в VS Code. В ней должен находиться `CMakeLists.txt`.

## Одна задача — одна ветка и Pull Request

Пример для новой задачи, когда текущие изменения уже сохранены в своей ветке:

```powershell
git status
git switch main
git pull --ff-only origin main
git switch -c feature/card-animation
```

`feature/card-animation` — пример имени; для исправления можно использовать `fix/ace-scoring`, для документации — `docs/demo-plan`. Перед началом договоритесь, кто меняет какие файлы. Особенно координируйте изменения в `src/main.cpp`.

После изменения кода выполните подходящие проверки ниже, затем просмотрите и сохраните только свои файлы. Пример для изменения правил:

```powershell
git diff
git add src/game/Game.cpp tests/game_tests.cpp
git diff --cached
git commit -m "fix: correct ace scoring"
git push -u origin HEAD
```

Замените список файлов и сообщение на соответствующие вашей задаче. Создайте на GitHub Pull Request (PR) из своей ветки в `main`. Укажите, что изменилось, как это проверить и какие проверки реально выполнены. Для графики приложите снимок или короткое видео.

Для дальнейшей работы команды рекомендуем сливать изменения после просмотра другим участником и прохождения доступных проверок. Это договорённость команды; документ не устанавливает настройки защиты ветки. Не переписывайте историю `main` и не используйте force push в общие ветки.

## Проверка изменений

Для правил, наград, магазина и переходов состояния:

```text
cmake --preset core-only
cmake --build --preset core-only --parallel
ctest --preset core-only
```

Добавляйте тест на изменённое поведение: например, автоматический GAME OVER, приоритет выполненной цели на последней раздаче, рост цели до 100, обновление Second Chance между раундами, выбор редкости с условным пересчётом весов, покупки/продажи или команду в недопустимой фазе. Один и тот же seed с одинаковыми действиями должен давать одинаковый результат. Сохраняйте отдельные RNG карт и магазина; изменение UI не должно менять колоду. Статистика проверяет вероятности, а не гарантирует проценты исходов в отдельном забеге.

Для графики, интерфейса и интеграции дополнительно:

```text
cmake --preset desktop
cmake --build --preset desktop --parallel
ctest --preset desktop
```

При рабочем OpenGL-контексте выполните smoke-прогон и запустите игру вручную. Путь ниже — Windows с генератором Visual Studio:

```powershell
.\build\desktop\Debug\blackjack_forge.exe --smoke
.\build\desktop\Debug\blackjack_forge.exe --demo --seed 42
```

Для Ninja/Linux путь отличается; см. README. Проверьте главное меню, START с переходом к столу, раздачу, магазин, продажу, завершение забега, настройки, изменение размера окна и изменённый эффект. `ctest` проверяет правила и не подтверждает качество картинки. Скрытое окно также требует GPU и графической сессии. В PR отдельно запишите результат CI и результат локальной проверки графики; если графика не запускалась, прямо укажите это. Не переносите результаты старого прототипа на новую механику без повторной проверки.

## Границы кода и ресурсы

- `src/game/` содержит правила и воспроизводимую случайность; без OpenGL, UI и таймеров анимации.
- `src/graphics/` рисует сцену; не определяет победителя и награды.
- `src/main.cpp` связывает ввод, UI, игру и сцену. Делайте небольшие согласованные PR; общий интерфейс модулей обсуждайте заранее.
- Не удаляйте чужие изменения при разрешении конфликта. Сначала выясните назначение обеих версий, затем соберите и проверьте результат.
- Не коммитьте `build/`, бинарники, `.pdb`, ZIP-архивы, временные снимки, токены, пароли и `.env`. Проверяйте `git status` и содержимое индекса перед коммитом.
- Сохраняйте лицензии `third_party/`. При намеренном обновлении зависимости обновите версию, исходный адрес и SHA-256 архива в `THIRD_PARTY_NOTICES.md`, объясните причину в PR и повторите сборку.
- Для новых картинок, моделей, шрифтов и звуков укажите автора, источник и лицензию. Добавляйте только материалы с подходящим разрешением на использование. Cormorant Garamond, Source Sans 3 и обе OFL находятся в `assets/fonts/`; будущие кастомные звуки и саундтреки требуют такого же учёта происхождения.
- Документация — на русском; идентификаторы и текущий UI — на английском. Обновляйте документацию при изменении поведения или сборки.

## Как сообщить об ошибке

Создайте issue с ожидаемым и фактическим поведением, шагами повтора и выводом `git rev-parse HEAD`. Для игровой ошибки добавьте seed и последовательность действий. Для графической — ОС, GPU, версию драйвера, размер окна, снимок и текст ошибок. Для сборки — компилятор, `cmake --version`, preset, точную команду и относящийся к ошибке лог без секретов.

## Содержание Pull Request

- Задача или ссылка на issue; краткое описание результата.
- Какие команды проверки выполнены и их результат.
- Для визуальных изменений — изображение/видео и проверенные состояния.
- Ограничения: например, другая ОС или машина преподавателя ещё не проверена.

Не включайте в один PR одновременно новую механику, большую переработку рендерера и форматирование всего проекта.
